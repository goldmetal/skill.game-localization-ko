# YAML·제어 문자열·팔레트 글꼴 구현

대상 구조는 [engine-profile.md](engine-profile.md)를 따른다. 현재 버전에서 이미 해결된 경로는 보존하고 요청과 관련된 부분을 수정한다.

## 1. 문자 소실과 폰트 문제 분리

대표 문자열에서 원본 파일 → 파서 출력 → 내부 변환 → 포맷 결과 → 폭 계산 → 그리기 입력을 필요한 경계만 확인한다.

| 관찰 | 다음 확인 |
|---|---|
| 파서 출력부터 잘못됨 | 실제 인코딩, BOM, 이스케이프, 파서·스키마 |
| 파서에서는 한글이지만 변환 후 `?`가 됨 | 문자표 변환·필터·대체 문자 분기 |
| 그리기 입력에 코드포인트가 남지만 네모로 표시됨 | 실제 선택 폰트, fallback, cmap·아틀라스 |
| 첫 글자만 보이거나 중간에서 끊김 | 내장 NULL, 잘못된 길이 계산, 고정 버퍼의 문자 분할 |
| 보이지만 정렬·줄바꿈이 다름 | 폭 계산과 렌더링의 글꼴·크기·자간 규칙 |
| 고정 UI는 되지만 이름·채팅이 실패함 | 입력·IME·저장·네트워크 경로를 별도로 조사 |

일반 텍스트 덤프가 바이너리 인수의 NULL에서 끝날 수 있다. 혼합 문자열은 필요한 범위의 바이트와 해석 결과를 함께 확인한다.

## 2. YAML 번역과 표시용 변환

yaml-cpp로 기준 영어·한국어 테이블을 읽고 숫자 ID, 헤더와 스칼라 값을 보존한다. 원본의 중복 ID는 파싱 단계에서 확인한다. 빈 문자열이나 `=` 같은 기호도 문자열 값일 수 있으므로 다른 YAML 파서의 암묵적 자료형 변환으로 바꾸지 않는다.

- 일반 텍스트는 UTF-8 코드포인트로 디코딩하고 `{INT16}`, `{STRINGID}`, `{COLOUR ...}`, `{NEWLINE}`, `{MOVE_X ...}` 등은 엔진의 명령 파서로 처리한다.
- 이미 원작 문자표에서 표현 가능한 문자·아이콘은 기존 코드를 사용하고, 원작 변환 함수가 대체 문자로 버리는 코드포인트만 표시용 확장 경로로 보낸다. 실제 `?`와 변환 실패를 구분한다.
- 언어 목록의 `native_name` 변환도 수정한다. 본문만 고치면 언어 선택 목록은 계속 깨질 수 있다.
- 영어 선로드·선택 언어 덮어쓰기와 `ko-KR` 설정, 원작 언어 ID 연결을 유지한다. CJK 기증 슬롯으로 같은 변환 병목을 우회할 수 있다고 가정하지 않는다.
- 기존 번역을 유지하면서 누락·의미 변경을 보완한다. 문자열 개수와 새 ID 범위는 현재 영어 테이블에서 계산한다.

## 3. 레거시 문자표와 바이너리 제어 코드를 쓰는 경우

이 계열에서는 C++ 소스에서 표시용 표현을 확장하는 경로를 사용한다. 현재 버전에 이미 동등한 유니코드 지원이 있으면 중복 태그를 추가하지 말고 그 구현을 검토해 재사용한다.

### 내부 표현 설계

원작 문자·색상·이미지·포맷 인수가 섞인 형식은 단순 UTF-8 교체로 깨질 수 있다. 현재 제어 코드 그룹 중 미사용 4바이트 인수 태그를 확인해 `태그 1바이트 + 코드포인트 인수 4바이트`로 보존하는 방식이 기존 순회 구조와 맞는다. 번호는 현재 소스에서 확정한다.

예를 들어 유니코드 인수 U+D55C는 Windows little-endian에서 `5C D5 00 00`이다. 태그를 포함하면 한 글자 토큰은 5바이트이며 내부 0바이트는 문자열 끝이 아니다. 추가 자간 플래그를 같은 인수에 담으면 코드포인트 마스크와 플래그 비트를 명시하고 모든 독자가 같은 규칙을 쓰게 한다.

- 태그 충돌과 인수 길이를 현재 버전에서 확인한다. 이전 패치의 태그 번호를 재사용 가능하다고 가정하지 않는다.
- 직렬화한다면 바이트 순서·폭·버전 표시를 명시한다. 저장·네트워크 경계와 내부 표시 버퍼를 구분한다.
- 코드포인트가 유효한 스칼라 값인지, 대체·거부·폴백 규칙이 무엇인지 정한다.
- 인수에 0바이트가 있으면 길이 지정 버퍼와 토큰 인식 순회를 사용한다.
- 공간이 모자랄 때 태그나 멀티바이트 문자를 중간에서 자르지 않는다. 종단 공간도 예산에 포함한다.
- YAML 변환 버퍼도 확장된 크기를 수용해야 한다. 유효 UTF-8의 2바이트 문자가 5바이트 토큰이 되는 최악 확장을 고려해 용량을 계산한다. 입력 바이트 수와 동일한 버퍼를 그대로 사용하지 않는다.
- 표시용 한국어가 기존 필드에 저장될 수 있으면 비패치 실행 파일과의 호환성·최대 길이를 별도로 기록한다.

### 관련 연산 통합

최소한 다음 경로가 같은 규칙을 사용하는지 확인한다.

```text
언어명/본문 로딩 → 포맷 인수 삽입 → 문자열 복사·길이 계산
                         ↓
           폭 계산·줄바꿈·자르기·정렬
                         ↓
              실제 그리기·티커·입력 커서
```

고정 버퍼를 쓰는 뉴스·로딩·자동 이름·시나리오 설명처럼 우회 복사 경로를 놓치지 않는다. `strlen` 검색 결과를 일괄 교체하지 말고 일반 문자열과 바이너리 혼합 문자열을 구분한다.

원본 DAT 언어 테이블의 물리적 길이·종료 규칙은 파일 형식의 규칙대로 읽는다. 렌더링용 문자열의 새 복사 규칙을 원본 파일 파싱에 일괄 적용해 오프셋을 바꾸지 않는다. 티커의 표시 글자 수는 5바이트 토큰을 한 문자로 세며 색상·레이아웃 명령을 일반 글자로 세지 않는다.

## 4. 한글 글리프 공급자 추가

Windows 구현의 기본 경로는 프로세스 전용 글꼴 등록과 GDI 래스터화다. 기존 G1 문자와 아이콘을 유지하고 확장 토큰을 만났을 때만 새 공급자를 호출한다.

1. 배포 가능한 픽셀 계열 한글 TTF를 실행 파일 옆 자산 경로에서 찾고 `AddFontResourceExW`의 프로세스 전용 옵션으로 등록한다. 종료 시 해제하고 시스템 전체에 설치하지 않는다.
2. 글꼴 face·크기·굵기를 선택하고 `GetGlyphOutlineW` 등으로 비트맵과 advance·bearing·baseline을 함께 얻는다. 글꼴 등록 성공과 실제 선택한 face를 구분해 확인한다.
3. 폰트·크기·스타일·코드포인트·렌더링 모드에 맞는 캐시 키를 사용한다. 필요한 경우 캐시 제한·해제·동시 접근도 처리한다.
4. 글리프 마스크를 8비트 RenderTarget의 기존 글자색·외곽선·그림자 팔레트로 출력한다. x/y/width/height·pitch·클리핑을 보존하고 창 내부 상대 좌표와 화면 좌표를 혼용하지 않는다.
5. medium normal·medium bold·small·large의 크기·기준선·굵기를 각각 확인한다. 글꼴 로드 실패와 빈 글리프를 탐지하고 사라진 문자를 정상 출력으로 처리하지 않는다.
6. 실제 그리기와 동일한 글리프 폭을 측정·줄바꿈·자르기에 사용한다.

초기 튜닝 참고값은 작은/보통/큰 글꼴의 7/10/18px, 한글 2px 하향 보정이다. 선택한 글꼴의 픽셀 설계·행 높이와 함께 확인한 뒤 조정하며 고정된 정답으로 쓰지 않는다. 다른 OS는 별도 공급자와 동일 렌더링 계약을 구현해야 하며, Windows 전용 코드가 빠진 상태를 지원 완료로 보고하지 않는다.

## 5. 번역·오브젝트·레이아웃

UI YAML, DAT 내장 명칭, 자동 생성 이름은 별도 경로다. DAT 문자열 로더에서 원작 언어 ID별 원문을 선택한 뒤 한국어용 표시 문자열을 교체한다. 임시 오브젝트와 정식 로드 객체에서 번역 문자열의 저장 수명도 보장한다.

런타임 번역 매핑이 필요하면 오브젝트 종류와 안정적인 ID를 우선 검토한다. 문자열 매칭만 가능하면 대상과 인덱스를 좁히고, 이름 변경 시 누락을 탐지하며 미등록 콘텐츠는 원문으로 폴백한다. 수정되지 않은 데이터의 전체 의미까지 번역했다고 보고하지 않는다.

화물은 품목명, 그래프용 단위, 단수·복수 수량 문자열이 따로 있을 수 있다. 숫자 인수 코드를 유지하면서 한국어 수량 표현을 구성한다. 건설 목록은 선로·신호 설명·역·추가 설비·교량·터널·도로·정류장·건널목을 종류별로 추적한다. 차량 모델명·지명까지 번역할지는 사용자 범위를 따른다.

레이아웃은 padding·콘텐츠 폭·정렬 기준·행간·클릭 영역을 함께 확인한다. 혼합 문자 경계 자간은 전역 공백 삽입 대신 측정과 그리기에 같은 규칙으로 적용한다. 외곽선·그림자·잘림·장문·확대 배율도 필요한 표면에서 확인한다.

이 계열의 픽셀 UI에서 검토할 출발점은 한글·라틴 경계 2px, 텍스트 드롭다운 행 14px, 툴팁 좌우 3px다. 실제 폰트·창 크기·배율을 보고 정한다. 붙여넣기 같은 긴 명령은 버튼·프레임·닫기 버튼·오른쪽 위젯을 함께 옮기고 화면에 글자만 억지로 밀어 넣지 않는다. 툴팁은 상자 폭과 중심점을 함께 조정해 양쪽 여백을 확보한다.

저장 데이터의 과거 잘림을 복구해야 한다면 결함 버전·필드·식별 가능한 패턴으로 조건을 좁힌다. 정상 사용자 이름을 추측으로 고치지 않는다.
